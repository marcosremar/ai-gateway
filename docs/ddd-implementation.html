A visão: Firebase-for-AI

O AI Gateway é um Backend-as-a-Service para aplicações de IA. Assim como o Firebase fornece auth, database, storage e compute para apps web/mobile, este sistema fornece os mesmos primitivos, mas especializados para workloads de inteligência artificial.

Firebase (apps web/mobile)

  • • Authentication
  • • Cloud Firestore
  • • Cloud Storage
  • • Cloud Functions
  • • Realtime Database
  • • Pub/Sub
  • • Firebase SDK

AI Gateway (apps de IA)

  • • Auth + API keys + Vault
  • • Neon PostgreSQL + Latency DB
  • • Object Storage (S3/R2/B2)
  • • Compute (GPU, Bots, DB workloads)
  • • State Store + WebSocket
  • • Event Bus
  • • Browser/TypeScript/Python SDK

O Core Domain

O coração do produto é fornecer acesso unificado a inteligência artificial. Não importa se a inferência roda numa API cloud (Groq, OpenAI, Fireworks) ou numa GPU self-hosted (RunPod, Vast.ai, TensorDock, Modal). O gateway abstrai isso.

Insight chave: Cloud providers e GPU providers não são domínios separados — são variantes do mesmo conceito. Ambos implementam a interface Provider e vivem no mesmo registry. A diferença é apenas o transport (API HTTP pública vs GPU provisionada).

Bounded Contexts

Gateway

Core

Acesso unificado a IA via cloud ou GPU. Contém providers (cloud + GPU), routing (fallback, racing, cache), pipeline (STT→LLM→TTS), deploy, autoscaler e proxy OpenAI-compatível.

src/gateway/
151 arquivos

Compute

Supporting

Deploy de workloads do usuário em infra remota: GPU pods, meeting bots (Recall.ai), databases (Neon) e image builder para imagens Docker customizadas.

src/compute/
12 arquivos

Events

Supporting

Event bus tipado + hooks de observabilidade. Permite comunicação entre contextos sem acoplamento direto. onRequestEnd, onScaleUp, onCostAlert.

src/events/
2 arquivos

Storage

Supporting

Object storage S3-compatible. Adapters para AWS, Cloudflare R2, Backblaze B2, MinIO e DigitalOcean Spaces. Usado para pesos de modelos, recordings, exports.

src/storage/
5 arquivos

Auth

Supporting

Autenticação via tokens HMAC-SHA256 e vault AES-256-GCM para secrets. Tokens de 60s para GPU pods e vault com rotação de chave master.

src/auth/
7 arquivos

Platform

Generic

Infraestrutura compartilhada: adapters (in-memory, Redis), DI contracts (StateStore, SettingsStore), logger, observability (tracing, metrics).

src/platform/
14 arquivos

As 8 fases da migração

  1. PreparaçãoAuditoria de thin wrappers, remoção de módulos não usados (secrets-rotation, gpu-state), correção da violação proxy→server.
  2. Extrair PlatformMover adapters, observability, deps, logger para src/platform/.
  3. Organizar serviçosRenomear event-bus→events, object-storage→storage, consolidar vault em auth.
  4. Unificar GatewayMover providers, gpu-providers, proxy, autoscaler para dentro de src/gateway/.
  5. Core domain em src/Extrair race-providers, ewma-tracker, speculative-cache, streaming-overlap de server/ para src/gateway/.
  6. Quebrar state.tsDecompor god object em 5 módulos domain-specific (deploy, readiness, standby, cost, metrics).
  7. Delivery layerScaffolding de server/routes/ + extração de 85 rotas de ws-server.ts.
  8. ComputeReorganizar workloads e image-builder em src/compute/.

Princípios mantidos

Zero breaking changes

Todos os caminhos antigos são preservados como barrel re-exports. Código consumidor nunca precisou ser atualizado.

src/ não importa server/

Regra mantida via CI. Lógica que depende de server/ usa Dependency Injection para receber deps.

Incremental, sem big bang

Migração em 6 commits, fase por fase. Cada commit compilava e mantinha o sistema funcional.

Monorepo preservado

Sem separação em múltiplos repositórios. Fronteiras explícitas em pastas e interfaces.

Ubiquitous Language

Vocabulário documentado em docs/domain-model.md. Toda entidade e evento tem nome canônico.

Context Map explícito

Regras de dependência entre contextos documentadas em docs/sdd.md.
