# Storage, Database, State & Config — 100 Optimizations (IDs 701-800)

> This audit covers S3-compatible object storage (`src/storage/`), the Prisma+Neon/raw-SQL database layer (`src/database/`, `server/latency-db.ts`, `server/prisma-init.ts`), the StateStore adapters (`src/platform/adapters/*`), connection pooling, the DI surfaces (`src/deps.ts`, `src/platform/deps.ts`), and the file-backed runtime state under `~/.babelcast/` (`server/*-persistence.ts`, `src/gateway/state/*`). The dominant findings cluster around four themes: (1) **non-atomic / un-flushed file writes** that can corrupt or silently drop state on crash — `daily_spend.json`, `cooldowns.json`, the `.bak` backup copy, and the registry/seed writes all write-in-place without `tmp+rename` or `fsync`; (2) **shutdown-time data loss** — the debounced `flushDailySpend()` / `saveCooldownState()` / `savePullHistoryNow()` are defined but never wired into the SIGINT/SIGTERM handler in `server/ws/pid-lock.ts`, so up to 10s of GPU-spend accounting and all cooldown state evaporate on every restart (a real cost-control hole); (3) **N+1 / non-transactional DB access** — `saveProbeResult()` issues five sequential dependent Prisma round-trips per probe with no `$transaction`, and `sortGpuTypesByLatency()` runs one query per GPU type in a loop; and (4) **read-modify-write races** on the provider-config file across concurrent HTTP handlers, plus the `src/modules/` tree being a 590-file near-duplicate of `src/` that has already drifted. Cost items focus on Neon egress/round-trips, S3 list/GET egress, connection reuse, and batching. Items are grounded in specific files and line numbers; recommendations are 1-2 sentences and do not modify source.

## Atomic Writes, fsync & Crash-Safety

## Shutdown Flush & Debounce Correctness

| ID | Optimization | Lens | Impact | Effort | Location | Recommendation |
|----|--------------|------|--------|--------|----------|----------------|
| 711 | `flushDailySpend()` never called on shutdown | Cost | High | S | server/ws/pid-lock.ts:101-103 | SIGINT/SIGTERM handlers call only `releasePidLock()` then `process.exit()`; the debounced 10s `daily_spend.json` write is dropped, so the budget gate re-arms each restart and can overspend the daily cap. | 712 | `saveCooldownState()` never wired to shutdown | Reliability | High | S | server/cooldown-persistence.ts:60-62 | The doc says "call on SIGTERM/SIGINT" but no handler invokes it; a restart loses all provider cooldowns and immediately re-hammers rate-limited/credit-exhausted providers (defeating ADR-009). | 713 | `savePullHistoryNow()` debounce lost on exit | Cost | Med | S | server/pull-history-persistence.ts:82-92 | The 10s debounced write is `unref()`'d, so on a clean exit within 10s the in-memory pull-time history is discarded and the next deploy reverts to the 30-min conservative timeout. | 714 | `stampAppRequest` flushes the wrong app on switch | Reliability | Med | S | server/config-persistence.ts:647-662 | While a stamp is pending, a later `stampAppRequest(otherApp)` overwrites `_pendingStampId`, so the first app's `lastRequestAt` is never recorded and only the last app in the window is stamped. | 716 | Daily-spend debounce has no max-staleness cap | Reliability | Med | S | src/gateway/state/cost-state.ts:89-96 | `_schedulePersist` coalesces all updates into a single trailing 10s write; a steady stream of spend updates with periodic crashes can lose nearly 10s of spend each cycle. ## Database Round-Trips, N+1 & Transactions
