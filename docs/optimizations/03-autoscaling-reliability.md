# Autoscaling, Reliability & Resilience — 100 Optimizations (IDs 201-300)

> Audit of `src/gateway/autoscaler/` (the real impls; `src/autoscaler/*` are 1-line re-export shims), `src/{canary,chaos,retry-policy,error-boundary,health-check,auto-remediation,memory-safe,memory-watcher}`, `src/timer-manager.ts`, and the server-side GPU lifecycle (`server/gpu-*`, `server/standby-pool*`, `server/latency-scheduler.ts`). The system is broadly defensive (cancellation flags on boot pollers, fail-closed rate limiting, double-flag orphan-nuke gating, persisted destroy timers) but has recurring cost and reliability gaps: several background `setInterval`/`setTimeout` timers are not `.unref()`'d (orphan sweep, standby pool/monitor, latency scheduler, destroy timer) so they can pin the process; the adaptive idle-timeout floor is **4 hours** (`MIN_IDLE_TIMEOUT_MS`) which dwarfs the documented 15-min/5-min stop policy and is a major idle-GPU cost risk; `IDLE_TIMEOUT_MS` is never seeded from its documented env var; `memory-watcher` permanently monkey-patches `global.setTimeout` and never restores it; crash-recovery and restart thresholds use exact `===` equality that can be skipped; the circuit breaker's advanced statistics live in non-persisted in-memory maps while the FSM is persisted; predictive warmup accumulates raw counts forever (no decay) so a one-time spike pre-warms a GPU indefinitely; and several modules (canary routing, EWMA `peak`) carry unused fields or non-sticky behavior. Cost items are heavily represented because idle/oversized GPU time is the dominant spend.
